# バレーボール ビデオスカウティングWebアプリ 仕様書

## 1. プロジェクト概要
バレーボールのスタッツ・分析ソフト（VolleyStation等）から出力される`.vsm`ファイルを読み込み、アップロードされた試合映像（YouTube）と同期させることで、特定のラリーやプレイを簡単に振り返ることができるWebアプリケーション。

## 2. システム構成（技術スタック）
*   **フロントエンド:** Next.js (React), TypeScript
*   **バックエンド (API):** Next.js API Routes (Serverless Functions)
*   **動画ホスティング:** YouTube (限定公開を利用)
*   **動画制御:** YouTube IFrame Player API (または `react-youtube` 等のラッパーライブラリ)
*   **ファイルストレージ:** Vercel Blob (無料枠を利用)
*   **ホスティング環境:** Vercel

## 3. コア機能要件

### 3.1 ファイルアップロード・解析機能
*   ユーザーがブラウザから `.vsm` ファイルを選択し、Vercel Blobへアップロードする。
*   アップロードされたファイルをバックエンドで解析し、プレイごとのメタデータ（アクション種類、選手、評価）と**動画タイムスタンプ（秒数）**を抽出する。

### 3.2 YouTube動画同期（シンクロ）機能
*   **オフセット設定:** 実際のYouTube動画の開始位置と、`.vsm`データの記録開始位置（0秒地点）の「ズレ」をユーザーが手動で設定できる機能。
*   **プリロール（Pre-roll）再生:** 記録されたジャストの秒数ではなく、プレイの助走や状況を把握できるよう、設定した秒数（例: 3〜5秒前）から再生を開始する機能。

### 3.3 ラリー閲覧・フィルタリング機能
*   解析されたデータをもとに、試合中のラリーやアクションをリスト表示する。
*   特定の選手、特定のアクション（スパイク、ブロック等）、またはラリーの勝敗などでリストをフィルタリングできる。
*   リスト内の項目をクリックすると、連携したYouTubeプレーヤーが該当のタイムスタンプへ自動でシーク（移動）し、再生を開始する。

## 4. データ連携と同期ロジック

動画の再生位置を決定するための計算式は以下の通りとする。

**再生位置(秒) = vsmデータのタイムスタンプ(秒) + オフセット(秒) - プリロール(秒)**

*   **vsmデータのタイムスタンプ:** ファイル解析により抽出されたアクション発生時刻。
*   **オフセット:** ユーザーが画面上で指定する動画とデータの差分時間。
*   **プリロール:** プレイ発生の数秒前から再生するための固定値（ユーザー設定可能が望ましい）。

## 6. インフラとデータフロー（フェーズ1）

初期開発（MVP）フェーズにおけるデータの流れは以下を想定する。

1.  ユーザーがWeb UIから `.vsm` ファイルとYouTube URLを指定。
2.  Next.js APIを経由して、`.vsm` ファイルを **Vercel Blob** へアップロード。
3.  ファイルのアップロード完了と同時にデータを解析（パース）し、JSON形式でフロントエンドへ返す。
4.  フロントエンドは受け取ったJSONデータをもとにリストを生成し、YouTube APIと連動して動画のシーク制御を行う。

*(※将来的にチーム共有機能などを実装する場合は、データベース（Vercel Postgres等）を導入し、動画URLやオフセット設定などのメタデータを永続化するフェーズ2へ移行する。)*

## 7. 開発方針
本アプリは、以下の2つを疎結合に実装する。

1.  **試合データ解析レイヤ**
    *   `.vsm` / `.vsdb` を読み込み、試合・セット・イベント・プレイ単位の正規化済みJSONへ変換する。
    *   動画同期に必要な `time` / `originalTime`、プレイ一覧、スコア推移、ローテーション情報を抽出する。
2.  **動画同期・分析UIレイヤ**
    *   正規化済みJSONを表示し、YouTubeプレーヤーとの同期、フィルタ、分析表示を行う。

この分離により、動画UIの変更とデータ解析ロジックの変更を独立して進められるようにする。

## 8. データモデル方針
サンプルデータの確認結果として、今回扱う `.vsm` / `.vsdb` は実体がJSONであり、`.vsdb` の `matches[*]` は `.vsm` とほぼ同型である。よって、アプリ内部では以下のような共通構造へ正規化する。

*   `Match`
    *   試合単位のメタデータ、チーム情報、セット一覧を持つ
*   `Set`
    *   セット番号、最終スコア、イベント一覧を持つ
*   `Event`
    *   ラリー進行中のスコア、ポイント結果、プレイ一覧を持つ
*   `Play`
    *   `team`, `player`, `skill`, `effect`, `code`, `time`, `originalTime` などを持つ
*   `Lineup`
    *   各イベント時点の `positions` と `setterAt` を持つ
*   `VideoSyncSettings`
    *   `youtubeUrl`, `offset`, `preroll` を持つ

MVPでは動画同期計算に `time` を採用し、必要であれば将来的に `originalTime` への切替を可能にする。

## 14. ストレージ切替
現在の実装では、ワークスペース保存先を環境変数で切り替えられる。

*   `WORKSPACE_STORE_PROVIDER=local`
    *   `.data/workspaces` 配下の JSON ファイルへ保存する
    *   ローカル開発向け
*   `WORKSPACE_STORE_PROVIDER=vercel-blob`
    *   `@vercel/blob` を使って `workspaces/*.json` として保存する
    *   `BLOB_READ_WRITE_TOKEN` の設定が必要

`WORKSPACE_STORE_PROVIDER` が未設定でも、`BLOB_READ_WRITE_TOKEN` が存在すれば `vercel-blob` を優先し、なければ `local` を使う。

## 15. 環境変数
`.env.example` を `.env.local` としてコピーし、必要な値を設定する。

```bash
cp .env.example .env.local
```

### ローカル開発
ローカル JSON 保存を使う場合:

```env
WORKSPACE_STORE_PROVIDER=local
```

環境変数ファイルを変更せず、確実にローカル保存で起動する場合:

```bash
npm run dev:local
```

このコマンドでは、Vercel CLIで取得したBlob用トークンがローカル環境に存在しても、
保存先として `.data` を優先する。保存場所は次の通り。

* 試合データ・動画ライブラリ: `.data/documents`
* 登録済みの試合ワークスペース: `.data/workspaces`

### ローカルで試合を登録する

1. `npm run dev:local` で起動する
2. ホーム画面から対象チームを開く
3. `試合データ管理` で `.vsm` または `.vsdb` を登録する
4. `動画ライブラリ` の `試合動画` フォルダへ YouTube URL を登録する
5. `設定` で試合名、試合データ、動画を選び、試合を登録する

必須の元データは試合データファイルとYouTube URL。試合名と対象チームは画面上で指定する。
動画とプレー時刻にずれがある場合のみ、セットごとのオフセット秒を調整する。複数セットで
同じ動画を使う場合は先頭セットだけに動画を指定すれば、後続セットへ引き継がれる。

Vercel Blob をローカルで試す場合:

```env
WORKSPACE_STORE_PROVIDER=vercel-blob
BLOB_READ_WRITE_TOKEN=your_token_here
```

### Vercel 本番
Vercel の Project Settings > Environment Variables に以下を設定する。

*   `WORKSPACE_STORE_PROVIDER=vercel-blob`
*   `BLOB_READ_WRITE_TOKEN=...`

この設定で、ワークスペース保存 API は自動的に Vercel Blob を使う。

## 16. 部内ページ(ログイン・名簿)
男子(`/t/utvb`)にだけ、部員とスタッフがログインして使う区画がある。試合ビューアの画面はログインなしのまま。

| URL | 中身 |
|---|---|
| `/t/utvb/login` | 部の合言葉を入れて、自分の名前を選ぶ |
| `/t/utvb/members` | 名簿。直せるのはトレーニング担当だけ |
| `/t/utvb/members/logins` | ログインの記録と、最後に開いた日時(トレーニング担当だけ) |

* ログインは、署名を付けたクッキー(`HttpOnly`、400日)。`middleware.ts` が開くたびに期限を延ばす。
* 合言葉(`PORTAL_PASSPHRASE`)を変えると、全員がログインし直しになる。
* **名簿の並び**:学年の上から、同じ学年の中は背番号の順(数字 → 文字 → なし)。`sortMembers` で、名簿を使うすべての一覧に効く。
* **背番号**:プレイヤーは数字、スタッフは T・M・C などの文字(4文字まで)。名簿に背番号(`members.number`)があれば、画面でも Slack の文でも、名前の前に付けて出す(`15林`。`Member.displayName`、SQL では `MEMBER_DISPLAY_NAME_SQL`)。取り込む表に「背番号」の列があるときだけ書き換える。
* 名簿はリポジトリに入れない。名簿が空のあいだは、合言葉を入れた人がログイン画面から Markdown の表を貼って取り込める。
* 保存先は Postgres。`DATABASE_URL` がなければ、ローカルでは `.data/portal-db`(PGlite)に保存する。Vercel では `DATABASE_URL` が必須。
* 表は `lib/server/portal-db.ts` の `MIGRATIONS` に書いてあり、最初の問い合わせのときに自動で作られる。変えるときは末尾に足す。

### トレーニング録
| URL | 中身 |
|---|---|
| `/t/utvb/training` | 自分の今週のメニューと、記録の入力(重さ・気になること・リーダーとトレーニング担当へ)。測定(体重・3RM)もここ。上に「みんなの記録を見る」ボタン(2026-11-07 から) |
| `/t/utvb/training/team` | みんなの記録(メイン3種目の重さ、推定1RM、スクワットの体重比、この週の記録(1回ごとに種目・重さ・回数・セット。2026-11-07 から)、書かれたこと)。ノートと同じく、上でポジションのまとまり(サイド・MB・S・Li・全員、`?group=`)を切り替える。開いたときは自分のまとまり、知らせのリンク(`?date=`)から来たときは全員(2026-11-07 から) |
| `/t/utvb/training/plan` | 年間の方針と、2か月ごとの位置付け。登録してあるメニューへの入口 |

* メニューはリポジトリに入れない。トレーニング担当が、画面の「メニュー・年間の方針を入れる」から `menu.json` を読み込ませる(データベースの `training_programs` に入る)。
* **メニューは期間ごとに何本も持てる。** 最初の週の開始日がキーで、同じ開始日のものは入れ替わり、違うものは足される(先の期間を前もって入れておける)。画面では `?menu=<開始日>` で切り替える。何も指定しなければ、今日が入る期間 → 次に始まる期間 → いちばん新しい過去の期間、の順で選ぶ(`pickProgram`)。
* 記録は週の開始日で持っているので、メニューを入れ替えても消しても残る。
* **年間の方針**は `plan.json`(`kind: "plan"`)を同じ画面から読み込ませる(`training_plans`)。区切りの日付で、メニューと結び付く。
* 段階・枠・ポジション・学年は名簿から取る。段階・枠がまだ決まっていない人は、画面で選べる。
* その週にやることの組み立ては `lib/domain/training.ts` の `resolveWeek`。
* 重さの欄には、メイン種目は目安(推定1RM × その週の%)、ほかの種目は前回の重さが最初から入る。
* **自重の種目**(プランク・ジャンプ・ノルディックなど)は、重さの欄に「自重」と出して数字は打たない。**懸垂・ディップス**は「自重+」で、足した重さ(加重)だけを打つ。どれに当たるかは種目名から決める(`weightModeOf`、2026-11-05 から)。
* **秒数の種目**(プランク・ポゴなど、メニューが「45秒 × 3」の形のもの)は、回数の欄が秒数になる。メニューの書き方(`秒`/`回`)で決め、なければ種目名で決める(`inferUnit`)。記録には `unit: "sec"` が付き、まとめは「45秒 × 3set」。自分で足した種目は「回で記録 / 秒で記録」を切り替えられる(2026-11-05 から)。
* **チェックの種目**(動的ストレッチ・肩のウォームアップなど、メニューが「10分」の形のもの、名前にストレッチ・モビリティ・ウォームアップが入るもの)は、重さ・回数ではなく「やった」のチェック。毎回チェックなしから始まり、チェックした日だけ残る(`unit: "check"`、2026-11-05 から)。
* 記録の欄の種目名の横に「▶ 動画」。メニューの動画の一覧(`collectVideoLinks`)から、名前がいちばん長く合うものを出す。自分で足した種目にも出る。
* **T0 の人**は、メニューの「T0の場合」の列を全部の種目で使う(それまではベンチだけだった)。`splitT0` で名前・回数・ポイントに分ける。
* 導入の週・測定の週のメイン種目も、「軽い重さで 8回 × 3」「3RMの測定 3回 × 3」「1RMの記録会 1回 × 3」と回数を書く(記録の欄がセットの数だけできるように)。
* 上半身の日は**日曜**(2026-11-05 から。それまでは土曜)。記録や個人の追加メニューに残っている曜日の名前 `sat` は、そのまま上半身の日を指す。
* 記録は全員に見える。スタッフ(ポジションなし)はメニューを見るだけで、記録はしない。
* **サイト全体が、部内ページの「通常の表示」と同じ見た目**(鉄色の地 + コートの床の色、暗い配色にも対応。単語帳の表示ではない)。試合ビューアの側は `app/globals.css` の先頭の変数(`--bg` `--surface` `--text` `--accent` など)で色を決め、末尾の「通常の表示:部品の形」で、ボタン・タブ・ヘッダーなどの形を上書きしている。色を直に書かず、変数か `color-mix()` を使うと、暗い配色でも成り立つ。
* 部内ページ(ログイン・名簿・トレーニング)は `app/t/[teamSlug]/(portal)/` にまとめ、共通の枠は `layout.tsx`、見た目は `portal.css`(クラス名は `tp-` で始める)。試合ビューアのヘッダーは、これらの画面では出さず、部内ページ用のバーに替える。
* **権限**:名簿とメニューを変えられるのは、役割が「トレーニング担当」の人だけ(`canAdminister`)。最後の1人は、役割を外すことも名簿から外すこともできない。
* **見た目の切り替え**:上のバーの「単語帳」スイッチで、通常の表示と単語帳の表示(配布版の単語帳版と同じ。英語の見出し・発音・赤シート・必修語)を切り替える。端末ごとにクッキー `portal_mode` で覚える。枠の `data-mode` を変えるだけで、中身は CSS(`.tp-std-only` / `.tp-tango-only`)で出し分ける。
* 「ルールと説明」の文章は `menu.json` の `ref`(HTML)から出す。読み込むときに `sanitizeRefHtml` で、文章と表のタグだけに絞る。

| `/t/utvb/notes/write?date=YYYY-MM-DD` | その日のノートを書く・直す(1人・1日に1つ) |
| `/t/utvb/notes/<id>` | 1つのノートとコメント |
| `/t/utvb/notes/print?month=YYYY-MM` | 月ごとのまとめ(印刷して PDF にする)。トレーニング担当・トレーナー(肩書が「トレーナー」の人)・ポジションのリーダー |

* 書けるのはプレイヤーだけ。読む・コメントするのは、ログインした全員。
* 書けるのは過去のどの日でも、先は明日の分まで。消せるのは、書いた本人とトレーニング担当(コメントも一緒に消える)。
* **練習日は、部の Google カレンダーから取る**(`lib/server/portal-calendar.ts`、10分ごとに読み直す)。「オフ」で始まる予定以外は、時刻つきも終日も対象。ノートの枠と出欠の日付に使う。
* カレンダーが未設定か読めないときは、日・火・木・土の決め打ちに戻り、オフの日などはトレーニング担当が例外として登録する(`practice_day_overrides`)。
* 新着のコメントは、書いた本人がそのノートを開くと読んだことになる(`notes.author_seen_at`)。上のバーの「ノート」に数が出る。
* **Slack の知らせ**(`lib/server/portal-slack.ts`):`SLACK_BOT_TOKEN` があり、名簿に Slack の ID がある人にだけ DM を送る。なければ何もしない。
    * ノートにコメントが付いた → 書いた本人
    * ノートに「リーダーへ」が書かれた → その人のまとまりのリーダー(OP は OH のリーダー)
    * トレーニング録に「リーダー・トレーニング担当へ」が書かれた → まとまりのリーダー + トレーニング担当・副担当

### 出欠の連絡
| URL | 中身 |
|---|---|
| `/t/utvb/attendance` | 遅刻・早退・欠席の連絡を出す・訂正する・取り消す。下に、練習ごとの出欠(ポジション別。連絡のない人は来られるものとして数える) |

* 連絡できるのは、ログインした全員(スタッフも)。1人・1日に1つで、出し直すと訂正になる。過ぎた日の連絡は出せない。
* 理由は必ず書く。**備考**(2026-11-06 から)は書かなくてよく、書いたときだけ出欠の一覧と Slack に出る(`attendance_reports.note`)。
* 出す・訂正する・取り消すたびに、Slack の遅刻・欠席のチャンネル(`SLACK_ATTENDANCE_CHANNEL`)に流れる。ボットをそのチャンネルに招待しておく。未設定なら、サイトにだけ残る。
* 文の形は `lib/domain/attendance.ts` の `formatAttendanceMessage`。
* 連絡は**3か月先の日まで**出せる(`ATTENDANCE_MONTHS_AHEAD`。2026-11-06 に2か月から延ばした)。
* **まとめて出す**(2026-11-06 から。授業で毎週火曜は 18:30 から、のような人のため):「毎週の遅刻・欠席をまとめて出す」で曜日・種類・時刻・理由を入れると、カレンダーにある3か月先までの練習の日からその曜日の日が並ぶ。外したい日は押して外し、`POST /api/portal/attendance/bulk` でまとめて出す(一度に60日まで)。もう出してある日は訂正になる。Slack には1通にまとめて流す(`formatBulkAttendanceMessage`)。

### 練習の集計(`/t/utvb/stats`)

* マネージャー・アナリスト(肩書)とシステム担当が、練習のメニューごとに数える。見るのは全員。
* **タブはスパイクとレセプション**(`?tab=spike|reception`、2026-11-06 から。何もなければスパイク)。タブでメニューを作ると、その種類になる。
* **サーブ・ディグはアーカイブ**(主将の依頼、2026-11-06):集計を取らなくなったのでタブから外した。コードとデータは残してあり、`?tab=serve` / `?tab=dig` で開けばこれまでの記録を見られる(メニューは作れない)。
* **レセプション**(2026-11-06 から。主将の依頼):部員ごとに ABパスの数と受けた数(`reception_stat_counts`)。数える画面は1人1行に「ABパス」「それ以外」の2つ。受ける人は「✎ 人」で選ぶ(AB/C/全員の OH・OP・Li を一度に。OP は 2026-11-07 から)。メニューの名前の候補は「レセプション」だけ(2026-11-07 から)。選び方は共有(`drill_stat_drills.reception_setup`)で、スパイクと同じく2秒ごとに同期する。月の順位は ABパス率(規定は月20本、`rankReception`)。
* **メニューを消す**のは、集計ページの見出しの右上の「⋯」から(2026-11-06 から。数える画面に出したままだと押しまちがえやすかった。`components/drill-menu.tsx`)。消す前に確認が出る。
* マネージャー・アナリスト(肩書)は、上のバーの「トレ録」が「集計」になる(2026-11-06 から。ホームのいちばん下まで行かなくて済むように)。
* **サーブ・ディグ**(2026-10-31 から):部員ごとに評価(# + ! - / =)の本数(`drill_stat_counts`)。
* **スパイク**(2026-11-06 から。主将の資料「スパイク練習②(前衛)」の決まり):部員・トスを上げたセッター・位置・サーブのレベルごとに決定数と打数(`spike_stat_counts`)。
  * 数える画面:最初に「✎ 人」で打つ人を前半・後半の攻撃チームに分け、セッターを選ぶ(AB/C/全員で一度に組める。前半・後半はポジションが偏らないように自動で分ける)。1人ずつは、名前の横の ↑↓ で 前半・後半・出ない を移す(2026-11-07 から。それまでは押すたびに循環)。上で種目(前衛・パイプ・シャー・二段L/R)・攻撃チームと、画面に並べるセッター(同時に何人かが上げるので**最大3人**。4人目を選ぶと最初に選んだ人が外れる)を選ぶ。1人1行で、セッターごとに「決定」「ミス」のボタン(押した数が出る)。
  * **何人かで同時に数えられる**(2026-11-06 から):組み方(前半・後半・セッター)はメニューごとにデータベースに持ち(`drill_stat_drills.spike_setup`)、画面は2秒ごとに `GET /api/portal/drill-stats/<id>/spike` で本数と組み方を取りにいく(画面を開いているときだけ)。自分が送っている途中の分があるときは、取ってきた本数を使わない。どのチーム・どのセッターを出すかは端末ごと(`localStorage`)。
  * 前衛の位置は名簿のポジション(OH/OP/MB)から。OH・OP が受けるサーブのレベル(Lv1 逆回転 / Lv2 スタンディングフローター / Lv3 ジャンプフローター)は**名簿で1人ずつ決める**(`members.serve_level`、全員 Lv1 から。2026-11-07 から。主将の依頼)。編集できるのはシステム担当と、OH・OP のリーダー(名簿の「枠・サーブLvをまとめて編集」)。数える画面では名前の下に表示するだけ。それまでの「10本中5本決定を2回続けたら自動で上げる」と「数える画面で切り替える」はやめた。
  * チーム戦(決定率)とセッター戦(決定本数)を下の帯に出す。ペナルティは前衛だけ。「何周目」の表示は 2026-11-07 にやめた(主将の依頼)。
  * 月の順位(`rankSpikers`・`rankSetters`):スパイカーは位置ごと(OH・OP はレベル別)、規定打数は月20打。セッターは位置ごとの決定/打数と合計の決定率。
